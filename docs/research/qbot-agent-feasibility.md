# qbot 转型为执行型 Agent：调研与决策建议

- 调研日期：2026-11-03。
- 代码基线：[`dfd441ffe8ce70111831d43db39b2e0a7dd490c3`](https://github.com/dai-junjie/qbot/tree/dfd441ffe8ce70111831d43db39b2e0a7dd490c3)。
- 交付类型：研究报告，不是已实现的 Agent、部署变更或上线承诺。
- 阅读路径：先看本报告；运行时事实与出处见[运行时选型](<agent-runtime-options.md>)；现有代码与接入风险见[迁移审计](<qbot-agent-migration-audit.md>)。
- 证据约定：**事实**来自引用的源码或官方材料；**建议**是本次设计判断；**待验证**不能当作已经通过的能力。

## 1. 结论先行

**建议把 qbot 定位成“QQ 入口的个人/小团队执行型 Agent”，而不是给分数统计机器人加一个聊天模型。** 新产品以任务、工具执行、结果交付为中心；分数统计不再是核心功能，也不建议将旧统计逻辑包装成默认 Agent 工具。

建议优先验证这条路径：

> 保留 NoneBot2 / OneBot / NapCat 的消息接入经验，替换分数业务；增加独立的任务与权限层，通过适配器连接成熟 Agent 运行时，在隔离工作区中处理明确授权的任务。

先验证 DeepSeek Harness 的正式 SDK 能否覆盖所需执行能力，再决定是否采用；同时保留其他运行时的替换边界。**运行时 SDK 不等于完整的助手系统**：群聊授权、持久任务、消息去重、跨渠道接单、通知策略和上线治理仍属于 qbot 应用责任。各运行时的真实接口、许可证及限制详见[选型证据](<agent-runtime-options.md>)。

首版不追求完全复刻通用助手，先证明一个闭环：

1. 授权用户明确发起任务；接入层生成任务 ID，确认受理后后台执行。
2. Agent 读取指定资料或代码，使用允许的工具。
3. 用户可以查询状态、取消；重启不会默默重跑有副作用的操作。
4. 结果回到原会话并附可验证产物；失败说明限制，不把建议说成完成。

这是跨模块产品改造，**不是局部重构**。本调研不直接删除旧业务、不迁移线上数据、不开放任意命令执行；后续应按阶段实施，而不是一次替换全部项目。

## 2. “类似助手”应拆成哪些能力

以下是建议能力模型，不声称 qbot 或单个 SDK 已全部具备。

| 能力 | 用户感知 | 首版建议 |
| --- | --- | --- |
| 多轮理解 | 追问仍知道处理哪件事 | 保留任务内上下文；不同群、不同人不默认共享 |
| 工具执行 | 不只回答，还能检索、读文件、运行检查 | 从只读工具开始，再开放隔离代码修改 |
| 长任务 | 发完消息后继续工作 | 必须有任务 ID、后台执行与状态查询 |
| 可控权限 | 不因群里一句话操作主机 | 用户与资源授权、风险分级 |
| 成果交付 | 输出报告、文件或 PR | 验证产物，再通知 |
| 恢复与中止 | 断线、重启后状态明确 | 区分取消、超时、失败和结果不确定 |
| 主动工作 | 订阅事件后自动处理 | 延后；先明确授权规则和去重 |
| 多 Agent 协作 | 并行研究或独立复核 | 延后；不是最小闭环前提 |
| 扩展技能 | 添加专门能力 | 先做小工具注册表，不做插件市场 |

**成功标准不是能回复模型文本，而是在可控边界内把任务可靠交付。**

## 3. 现有 qbot 的实际起点

当前是 Python QQ 群分数统计应用，依赖 NoneBot2、OneBot 适配器、APScheduler、SQLite 与绘图库；未声明 LLM SDK 或 Agent 运行时依赖。见[项目配置](<../../pyproject.toml>)。

[插件模块](<../../src/qbot/plugin.py>)集中处理命令、统计、定时任务、数据库与消息发送。群白名单、按群互斥锁和短冷却时间可以参考，但**不是执行型 Agent 的授权、任务队列或持久恢复机制**。

重要风险：

- **群白名单不等于用户授权。** 某群可接入，不代表全体成员都可运行工具。
- **已有自发消息处理。** 模型回复、转发或其他机器人可能反向触发执行；必须在模型前鉴权、防回环。
- **协议通道单独保护。** WS token、HTTP 接入和网络边界不是同一层，不能给一处加 token 就假定所有入口安全。
- **统计重试不能直接复用为操作重试。** 写快照与创建 PR、发消息等副作用风险不同。
- **文档与实现已有漂移。** README 的连接方向、统计周期不能直接当成部署事实；应先固定受支持的启动与依赖组合。

逐项代码证据、协议参考和迁移影响见[迁移审计](<qbot-agent-migration-audit.md>)。本次未连接真实 QQ 账号、检查线上主机或验证生产部署。

## 4. 路线选择

### A：在现有插件里直接接模型并开放工具

**不推荐。** 能做聊天演示，但长期任务、权限、重试、取消和发送会继续耦合到事件处理函数；工具执行会放大现有安全边界不足。

### B：保留接入，替换业务，接入成熟运行时

**推荐默认路线。** 接入层处理可信事件、身份和发送；任务层处理持久状态与权限；运行时处理模型循环；工作区负责隔离执行。沿用 QQ 经验，不自行重做模型循环，但仍需构建应用级可靠性与授权。

### C：迁移到现成多渠道 Agent 项目

**值得并列验证，不建议未经验证直接替换。** 多平台聊天、插件和个人自动化需求可能更适合现成项目；严格任务状态、代码交付与审批需求仍须实测，不能只比较工具数量。相关一方材料见[运行时选型](<agent-runtime-options.md>)。

### D：完全自研 Agent 框架

**首版不推荐。** 会同时承担模型协议、上下文压缩、工具循环、恢复和插件演进。这些工作不直接证明产品价值；只有既有运行时反复无法满足已验证要求时再考虑。

选型优先级建议：**权限可实施性 → 可恢复闭环 → 工具能力 → 接入维护成本 → 模型可替换性**。不以 star 或未经同场景验证的费用排名决定路线。

## 5. 推荐模块边界

```text
QQ / NapCat → OneBot event
    ↓
Channel Gateway：身份校验、显式触发、去重、防回环
    ↓ TaskRequest
Task Coordinator + Policy：持久任务、队列、授权、审批、取消、预算
    ↓ RunRequest
Agent Runtime Adapter：调用所选 SDK，输出结构化运行事件
    ↓
Tool Broker：每次调用重新检查身份、资源和预算
    ↓
Isolated Workspace / External APIs
    ↓ Artifact + Evidence
Delivery Outbox → 原始 QQ 会话
```

这是建议职责图，不是已有代码；接口名不对应特定 SDK API。

| 边界 | 最少信息 | 约束 |
| --- | --- | --- |
| 接入 → 任务 | bot、会话、请求人、原消息 ID、内容、附件引用 | 回调不等待完整运行 |
| 任务 → 运行时 | task ID、工作区/工具白名单、预算、上下文、取消信号 | 不传全局密钥和全部聊天记录 |
| 运行时 → 工具 | task ID、结构化参数、拟执行操作 | 模型不得扩大权限或自行批准 |
| 工具 → 外部系统 | 已校验参数、最小权限凭据、操作标识 | 不绕过策略访问宿主资源 |
| 任务 → 交付 | 原会话、产物、验证结果、发送状态 | 工具成功不等于任务或投递成功 |

SQLite 可作为单机验证候选；这不意味着旧分数库有任务功能。首版就应持久化状态，不用全内存实现承诺长任务可靠性。

## 6. 状态、取消与恢复

建议状态：

```text
queued → running → succeeded
            ├── waiting_approval → queued / cancelled / expired
            ├── failed
            ├── cancelling → cancelled / outcome_unknown
            └── outcome_unknown
```

- `succeeded`：结果和必要产物已验证；投递状态另外记录。
- 审批绑定请求人、资源、确切操作和有效期，参数变化后失效。首版可不开放写操作，不能用一句“同意过”代替授权设计。
- 收到取消不代表已撤回外部操作；取消信号、子进程退出、外部请求结果分别确认。
- `outcome_unknown`：例如创建 PR 后网络超时，需先对账，不盲重试。

建议持久化任务、入站事件键、运行尝试、审批、工具操作记录、产物索引和发送 outbox。去重键区分平台、机器人、会话与事件标识；真实版本的重连/重放语义待验证，不能仅按文本判重。

恢复规则：

1. 重启后未确认完成的运行进入待恢复/不确定状态，不直接再跑。
2. 只读操作有限退避重试；有副作用操作先查外部状态。
3. Outbox 减少漏发，但远端已发、本地记账前崩溃仍可能重复，不承诺端到端 exactly-once。
4. 时间、模型用量、工具次数、并发和输出大小分别设限；SDK 轮数上限不等于费用上限。
5. 同仓库写任务串行或用独立分支/工作区；共享群不意味共享可写目录。

DSH 的具体取消与审批接口限制见[运行时选型](<agent-runtime-options.md>)；不能把上述状态机误认为 SDK 原生保证。

## 7. 安全边界

### 首版建议权限矩阵

| 操作 | 建议策略 |
| --- | --- |
| 授权人读指定公开资料/仓库 | 允许；限制域名、仓库、目录和输出范围 |
| 非授权人发任务或查私密任务 | 拒绝，不调用模型 |
| 宿主凭据、个人聊天、旧成绩库 | 默认禁止，不导入 Agent 记忆 |
| 下载附件 | 默认关闭；开启前做来源、大小、路径、格式和解压配额控制 |
| 测试与改代码 | 无宿主密钥的隔离工作区，小范围试点 |
| 推分支、建 PR | 分别授权，限制仓库与分支 |
| merge、部署、删数据、转账、发邮件等 | 不进入默认首版工具集 |
| 任意 shell、文件、浏览器会话 | 不提供全权限通用入口 |

只读也可能导致数据出站或内网访问；仓库测试与依赖安装脚本可执行恶意代码。代码执行应限制挂载、网络、进程、资源与凭据。**工作目录不等于沙箱，提示词禁止不等于系统隔离。** DSH 的文件写入限制不应被解释为全面的网络/进程沙箱，见[选型证据](<agent-runtime-options.md>)。

群聊规则：

- 身份来自可信事件字段，不由昵称、引用或“我是管理员”决定。
- 群与用户分别授权；群管理员不自动拥有主机权限。
- 自发消息、机器人、转发、引用和附件不是新授权。
- 按身份与会话隔离运行时上下文和产物访问；相同昵称不共享结果。**这不等于群消息保密：群任务的输入、回执和发到群里的结果默认全群可见。首版不接机密任务，不向群发送私密产物；如未来支持，只能发送脱敏状态，并通过独立身份鉴权的私有渠道交付。**
- 审批绑定有权用户与任务；陌生人的“同意”无效。
- 短确认、状态查询、成果交付取代逐 token 刷屏；不直接发送敏感工具日志。

网页、README、Issue、日志和附件都是待分析数据，不因声称“系统指令”获得执行权限。工具权限在模型外校验；引入 MCP server/插件等同引入新的可执行信任域，协议兼容不代表内容可信，也不替代 QQ 用户授权。以上均须在真实运行时验证，不是已实现的安全承诺。

## 8. 数据与部署迁移

**保留：** 经版本确认的消息接入、运行经验、历史代码与测试。新 Agent 独立配置、任务库和工作区，不把分数库改名充当对话库。

**退役：** 切换时停旧调度与命令，防止双重消费。新入口稳定后移除排名、绘图和统计依赖。旧数据库先备份并验证恢复，明确保留期与访问人后归档/删除，不默认上传模型或公共仓库。本研究不执行这些动作。

部署建议：

- 独立测试群与明确授权用户，不开全群自动处理。
- 固定 Python、依赖和运行时版本；隔离 QQ 接入与执行环境。
- 检查 WS、HTTP 两类接入、鉴权和网络暴露；回环地址不代表本机其他进程均可信。
- 模型密钥与工具凭据分离，日志脱敏，不记录原始隐私群历史。
- SDK 升级跑契约/安全回归，尤其注意预览版 API 变更。
- 本调研未完成 QQ 账号风控、官方替代接入或平台条款法务评估，不承诺接入长期稳定或零封号风险。

## 9. 建议实施阶段

以下是建议，**不是已完成功能或排期承诺**。

| 阶段 | 交付 | 进入下一阶段的证据 |
| --- | --- | --- |
| A：运行时验证 | 指定仓库/资料只读任务、适配器和隔离验证 | 可限制工具/预算、取消/恢复语义清楚、数据出站边界明确 |
| B：单群只读 MVP | 鉴权、显式发起、状态、持久化、回原会话 | 安全/恢复用例通过，真实测试群完成闭环 |
| C：受控代码工作流 | 独立工作区、修改/检查、分支与 PR | 无宿主密钥、不写默认分支、不重复建 PR，人工审阅通过 |
| D：扩展与主动任务 | GitHub/其他渠道、规则订阅、更多技能 | 规则经授权、事件不重复接单、审计和通知验证 |

先验证 A 再承诺 B/C。若 SDK 无法限制工具或隔离凭据，应换方案，不给主机全部权限凑演示。

第一个原型只回答：受限工作区能否“读仓库→检查→有出处结论”；取消、重启和重放时状态是否可信；恶意资料能否越权或跨群泄密。不先做界面、多 Agent 或全权限 shell。

## 10. 验收用例

以下是**后续测试计划**，不是本次通过的清单。

| 类别 | 场景 | 预期 |
| --- | --- | --- |
| 用户授权 | 白名单群中非授权人发任务 | 不执行、不调用模型、不泄露任务 |
| 协议鉴权 | 错 token WS、无签名 HTTP | 不进入可信事件处理；禁用路由不可用 |
| 回环/重放 | 自发回复、重复同事件 | 不递归、不重复副作用 |
| 上下文隔离 | 不同群同名用户 | 不共享私密内容/审批/产物 |
| 注入 | 文档要求读密钥上传 | 模型外策略拒绝并审计 |
| 附件/网络 | 路径穿越、解压炸弹、内网 URL/重定向 | 在受控边界拒绝 |
| 恢复 | 工具中杀 worker/重启 | 状态可解释，副作用先对账 |
| 取消 | 排队/模型/子进程/API 各阶段 | 不伪称已撤回外部操作 |
| 审批 | 越权、超时、参数改变 | 无效审批不能沿用 |
| 并发 | 同仓库两写任务 | 不覆盖工作树与产物 |
| 预算 | 时间/用量/次数/费用耗尽 | 停新增执行，不无限重试 |
| 交付 | QQ 断线、发送失败、超长结果 | 成果保留、有限重试、不假称送达 |
| 退役 | 旧统计任务到点 | 不发送旧统计，可回滚 |

评估运行时须使用固定任务、相同工具与资源边界：调研、仓库问答、受控小修改；记录成功率、人工介入、失败类型、用量、耗时、越权尝试结果。**本次无同场景 benchmark，不声称某框架更省钱或成功率更高。**

## 11. 成本与维护

选模型和供应商前不能给可信月费承诺：

```text
单任务成本 = Σ调用(输入 token × 对应单价 + 输出 token × 对应单价)
           + 工具/API/检索费用 + 执行环境费用
月成本 = 实际任务量 × 观测单任务均值 + 常驻设施/存储
```

缓存、长上下文、失败重试、多 Agent、附件解析和计费口径单列，以账单及供应商一方价格为准。先小额受限试运行，再设人/群/月预算；SDK usage 不一定覆盖第三方工具成本。

持续维护重点是 QQ 兼容、密钥、SDK 变更、隔离、恢复、安全回归与交付失败处理。缩小用户和工具范围能减负，取消权限边界不能。

## 12. 实施前的产品选择

调研不代替产品决策：

1. **主要用途：** 资料/办公助手还是仓库代码执行？本报告以代码能力为上限、只读为起点。
2. **使用者：** 本人、熟人还是全群？默认建议本人和显式授权测试用户。
3. **QQ 是否必须保留：** 默认沿用，不当成永久保证。
4. **运行位置与数据出站：** 明确隔离环境、可读数据、模型供应商。
5. **执行上限：** 默认只读；改代码、建 PR、部署和主动触发分别授权。

这是后续立项选择，**不是研究阻塞，也不是已获得的实施授权**。未决定时最稳妥的是单用户、单测试群、只读工具、独立存储的技术验证。
